# Deep Research 现存不足与改进方向

> 制定日期：2026-08-05（本次链路优化 commit `f1048c7` 之后）
> 分析方法：只读核查 extract_evidence / audit_gaps / embedding_service / search_service / runner / phase_service / 前端实际代码
> 分级原则：按"证据强度 × 影响范围"分级，区分已验证问题与推断性风险，不把安全/正确性/性能/功能混在同一体系
> 前提：用户当前采用 Semantic Scholar 无 key 模式运行

本次优化（O1/O2/O5a/O7/评分校准/前端 Gap 视图）解决了"闸门串联即终止、上游供给不足、幻觉"的结构性问题，但引入与暴露了新的薄弱环节。以下按优先级排列。

---

## 一、高优先级（已验证，影响大）

### 1. ChromaDB 无向量维度校验与迁移，切换 embedding 模型会静默失效

这是本次 O5a 改动引入的最大隐患。`EMBEDDING_DIM=1536` 仅是配置常量，代码里从未用它校验 API 返回向量的实际长度；`rag_service.py` 用 `get_or_create_collection` 建集合，不带维度参数、无迁移、无清空逻辑，集合维度由首次写入的向量隐式决定。

后果是：如果本地 `chroma_db/` 目录里残留了历史用本地 bge（768 维）写入的向量，切换到 API embedding（1536 维）后，`collection.add` / `collection.query` 传入 1536 维会触发 ChromaDB 的维度不匹配异常。索引侧异常被 `fetch_and_index_papers` 吞掉（该论文索引失败但任务续跑），检索侧异常在 `rag_retrieve_sync` 被 catch 返回空——也就是说，全文 RAG 会静默失效，用户看不到任何报错，只是效果退回摘要级。`sync_chromadb_with_sqlite` / `reembed_from_sqlite` 只补缺失、不检测维度，无法自愈。

改进方向：在 collection 的 metadata 里写入 embedding 模型名与维度版本键，服务启动时检测；发现与当前配置不符就自动重建集合（或明确报错要求手工清空）。同时在 `_embed_texts_api` 里用 `EMBEDDING_DIM` 校验返回长度，不符即抛出清晰错误，而不是让脏数据流入。这项改动小、收益大，应优先做。

### 2. 无 key 环境下 Gap 审计会系统性判 uncertain，导致产不出 Idea

`audit_gaps.py` 的准入门要求：至少 2 个完成查询、2 个 query family、成功率 ≥50%、至少 3 篇 gap 专属论文、以及存在外部近邻，任一不满足就直接判 uncertain 不进LLM 审计。这个设计本身是对的（证据不足时保守，不走过场放行）。

但它与"无 key 模式"叠加会产生系统性偏差：无 key 时 S2 限速 20/min 且易触发 429 进入 60 秒冷却，近邻检索变稀疏，准入门大概率因"gap 专属论文不足"或"无外部近邻"失败，于是几乎所有 gap 停在 uncertain 无法 surviving。结果不是"误放低质量 gap"，而是"几乎没有 gap 能通过审计"——进而触发 O2 补检索、耗尽预算、最终只产出 Landscape Brief。也就是说，在你当前选择的无 key 模式下，管线很可能产不出可信 Idea。

这解释了历史上"频繁卡在more_research_required"的现象，根因在上游供给而非审计逻辑本身。改进方向有三条可组合：无 key 时动态放宽准入门阈值（如 gap 专属论文从 3 降到 2、允许仅用 arXiv/OpenAlex 近邻）；提高 arXiv / OpenAlex / Crossref 在近邻检索中的权重以补偿 S2 缺位；在前端明确提示"当前检索源受限，可能影响缺口审计通过率"。这是让无 key 模式真正可用的关键。

### 3. 无 LLM 调用预算与分阶段超时，仅有单一 60 分钟顶层超时

一次完整任务的 LLM 调用量级是数百次——评分对每篇论文各调一次、证据抽取对每篇每chunk 各调一次（最多 30 篇 × 多 chunk）、VLM 对每张图各调一次、审计对每个 gap 各调一次、加上 Idea 生成的 7 处以上调用。而超时控制只有一个顶层 `AGENT_TIMEOUT=3600s`，既没有每阶段超时，也没有 token/调用次数预算熔断，成本不可预测。O2 补检索还会再叠加最多 3 轮。

25-30 分钟超时的主要风险点：PDF 下载与 embedding 索引在事件循环里同步阻塞（`embed_and_store_chunks_async` 注释明确 synchronously in event loop）；S2 的 429 冷却链每次 60 秒累积；证据抽取 30 篇 × 多 chunk 但并发只有 3；VLM 每张图 5-10 秒，图多时爆炸。

改进方向：把 embedding 索引和 VLM 描述移出事件循环（真正的 to_thread 或独立worker）；加每阶段超时和全局调用/token 预算熔断，超预算时优雅降级到已有产出而非硬超时；证据抽取和评分的并发度可调。

## 二、中优先级（已验证，影响中等）

### 4. 僵尸检索源，源健康度对用户不透明

当前源列表有 6 个，但 IEEE 和 CORE 都是必需 key、无 key 时静默返回空。也就是说默认部署实际只有 arXiv、OpenAlex、Crossref 和限速的 S2 四源有效，IEEE/CORE 是占位但零产出的"僵尸源"。用户不配key 会误以为覆盖 6 源。降级行为本身是好的（单源失败双层catch、429 冷却、不拖垮整体），问题在于不透明。

改进方向：启动时探测各源可用性，日志与 UI 明确汇报"实际启用 N/6 源"；无 key 的源直接降级为不加载，避免每次都发无效请求。

### 5. 证据质量的两个隐患：verified状态无产生路径 + abstract_only 被当有效证据

证据抽取确实做了真实的原文 span 回溯校验（全文路径下 span 定位失败就丢弃该证据，不是仅靠 LLM 自报），这点是可靠的。但有两个隐患：一是 `verification_status`代码里只会写入 unverified / abstract_only / upgraded，从不产生 verified，`extraction_confidence` 也是硬编码常量（全文 0.8、摘要 0.4）而非校验结果，所以这个置信度字段的区分力有限。二是 readiness gate 只排除 rejected / conflicted 状态，abstract_only（仅摘要、span 校验较弱）会被当作有效证据参与 gap 挖掘——PDF 下载失败率越高，弱证据占比越高，越容易驱动出证据不扎实的 gap。

改进方向：在 gap 挖掘时对 abstract_only 证据降权；把 extraction_confidence 改为反映实际校验强度（如span 精确匹配 vs 模糊匹配给不同分）；补上 verified 的产生路径或移除该枚举值以免误导。

### 6. 后端大量产出未在前端暴露，可解释性差

后端产出了干预方案（Intervention）、Landscape Brief、覆盖矩阵（Coverage Matrix）、gap 的近邻对比与审计记录、研究问题树，但前端大多看不到：Intervention 既无 API 路由也无视图；Landscape Brief 无独立端点无视图（只在失败时生成，前端无处展示）；Coverage 有 `/tasks/{id}/coverage` 端点但前端无视图；gap 的 `/gaps/{id}/neighbors` 和 `/gaps/{id}/audits` 端点存在但前端未调用；问题树无可视化。本次新增的 GapsView 是唯一的新视图，也只展示 gap 字段和 A/B 分档，不展示审计的近邻对比。

结果是用户只能看到最终 Idea 和 gap 列表，中间的证据链和推理过程不可见，系统的"证据驱动"卖点在UI 上体现不足。改进方向：补 Coverage 视图、Intervention 视图、Landscape Brief 视图，以及 gap 详情里的近邻对比与审计记录展示；给Intervention 和 Landscape 补只读 API 端点。

### 7. 高危路径测试覆盖薄弱

新增能力多为单元测试，缺集成/端到端覆盖，且恰好高危路径没测到：O2 回环只有决策逻辑单元测试，没有"闸门失败→补检索→重试→预算耗尽"的完整路径集成测试；O5a embedding 有 API mock 测试但没有维度不匹配、ChromaDB 混维场景测试（正是第 1 项高危点）；O7 预过滤无专门测试。既有失败的 `test_opportunity_pipeline_is_lineage_safe_and_idempotent` 经确认是测试环境/迁移对齐问题（fixture 用 alembic upgrade 建全表，与当前 models/断言存在字段对齐差异），非核心逻辑 bug，但长期挂着会掩盖真实回归。

改进方向：为维度冲突、无 key 审计、O2 完整回环补集成测试；修复或明确标记既有 WIP 测试。

## 三、低优先级（推断性风险，边界情况）

### 8. O2 remediation 计数器持久化时机

remediation 的 `remediation_attempts` 计数器在 `save_state` 时才持久化，round 号先自增。若在 save_state 之前崩溃，恢复后计数可能丢失，理论上可能超预算多跑几轮。崩溃恢复时 current_round 用 research_rounds 表 MAX 校准、remediation 也写了 round 记录，所以大部分情况能对齐，这是异常路径的边界问题，影响有限。改进方向：把计数器自增与 round 记录写入放到同一事务，或在自增 round 前先持久化计数。

### 9. 并发写边界

SQLite WAL + busy_timeout=30000 + max_concurrent_agents=2，两任务并发写不同 task_id 的行冲突概率低但非零；证据抽取每个并发子任务开独立 Session，瞬时写连接较多，长事务可能触及 busy_timeout。当前规模下不是致命问题，但若要支持更多并发用户，应按 docs/08 的设计迁移到 PostgreSQL。

## 四、改进优先级建议

若按投入产出排序，建议顺序为：先做第 1 项（ChromaDB 维度守卫，改动小、防静默失效）和第 2 项（无 key 审计放宽，直接决定当前模式能否产出 Idea），这两项是让系统"当前配置下真正可用"的关键；其次做第 3 项（超时与预算熔断，解决稳定性）和第 4 项（源健康度透明）；然后是第 5、6、7 项（证据降权、前端暴露、测试补齐）提升质量与可解释性；第 8、9 项作为长期演进按需处理。

一句话总结：本次优化把链路从"必然空手"改成了"有机会产出并诚实降级"，但在当前无 key 模式下，真正的产出瓶颈已从"闸门逻辑"转移到"上游检索供给不足导致审计判 uncertain"，同时 O5a 引入的 ChromaDB 维度隐患需要尽快加守卫。这两点是下一步最值得动手的地方。

## 五、实施状态（2026-08-05 更新）

第 1-7 项已全部实施完成，第 8、9 项作为长期演进保留。

第 1 项 ChromaDB 维度守卫：`rag_service.py` 抽出 `_get_or_recreate_collection`，在 collection metadata 写入 embedding 签名（后端:模型:维度），启动检测到漂移即自动重建；`embedding_service` 校验 API 返回向量长度不符即抛错。

第 2 项 无 key 审计放宽：`config.py` 新增 `constrained_retrieval_mode` 与放宽阈值，`audit_gaps.py` 按受限模式选阈值，Landscape Brief 加检索受限提示。

第 3 项 预算熔断 + 解除阻塞：`llm/base.py` 加 `LLMBudgetExceeded`与预算追踪，`venus_provider._post` 接入，runner 设预算并捕获降级；embedding 索引改回 `to_thread`。

第 4 项 源健康度透明：`PaperSource.is_available()`，IEEE/CORE 无 key 不加载，`SearchService` 报告生效源数并提供 `source_health()`。

第 5 项 abstract_only 降权：`mine_gaps.py` 当 limitation 信号全为摘要级时把证据档位 A 降 B（只降档不拦截）。

第 6 项 前端暴露：新增 Intervention 只读 API 路由；前端新增覆盖度视图、干预方案视图，Gap 详情可展开查看审计与近邻对比。

第 7 项 测试补齐：新增 `test_llm_budget.py`、`test_priority_fixes.py`，扩充 `test_embedding_service.py` 的维度校验用例；后端 199 个测试通过。既有 `test_opportunity_pipeline_e2e.py`（2 用例）仍为迁移对齐 WIP，与本次逻辑无关。

尚未实施：第 8 项（O2 计数器持久化时机）、第 9 项（PostgreSQL 迁移），均为长期演进项，当前规模下非瓶颈。
