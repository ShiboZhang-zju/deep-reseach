## 二、各环节问题分析

### 环节1：检索（Search）— 严重不足

#### 问题1.1：Semantic Scholar 大量限流（429）
**实测证据**：服务器日志中大量 `HTTP/1.1 429` 响应
```
2026-07-20 18:23:21 GET https://api.semanticscholar.org/.../search?query=... "HTTP/1.1 429 "
2026-07-20 18:23:22 GET https://api.semanticscholar.org/.../search?query=... "HTTP/1.1 429 "
2026-07-20 18:41:34 Source 'semantic_scholar' entered 60s cooldown (429)
```

**影响**：S2 是质量最高的学术检索源（含引用关系、venue等），限流导致大量经典论文缺失。配置中 `SEMANTIC_SCHOLAR_API_KEY` 为空，无 key 限速 20 req/min，元数据补充时瞬间打爆。

**根因**：
- `.env` 中 `SEMANTIC_SCHOLAR_API_KEY=` 为空
- `metadata_enrichment.py` 对 107 篇论文并发查询 S2，瞬间触发限流
- 限流后冷却 60s，但这期间所有 S2 检索全部跳过

#### 问题1.2：检索精度低，大量不相关论文
**实测证据**：搜索 "graph neural networks for test oracle generation" 返回了：
- 肝癌分类论文（Hybrid deep learning-based strategy for the hepatocellular carcinoma）
- 人脸识别论文（Investigações sobre redes neurais artificiais para o reconhecimento de faces）
- 上下文赌博论文（Taming the Monster: A Fast and Simple Algorithm for Contextual Bandits）

**根因**：
- 检索源（尤其 Crossref、CORE）使用全文搜索，关键词匹配精度低
- 没有对检索结果做预过滤（pre-filter），直接全部入库
- 6 个源 × 5 query × 15 papers = 450 篇/轮，大量是噪声

#### 问题1.3：去重率波动大但未有效利用
**实测数据**：
| 轮次 | found | new | dup_rate |
|------|-------|-----|----------|
| 1 | 225 | 132 | 0.41 |
| 2 | 176 | 82 | 0.53 |
| 3 | 165 | 95 | 0.42 |
| 4 | 171 | 85 | 0.50 |
| 5 | 164 | 42 | 0.74 |
| 6 | 175 | 57 | 0.67 |

第5轮 dup_rate=0.74 已触发终止条件（>0.75 且 ≥2轮），但因为先检查 max_rounds 所以继续跑了第6轮。

#### 问题1.4：元数据缺失严重
**全局统计**（4529篇论文）：
| 字段 | 完整率 |
|------|--------|
| DOI | 53.2% |
| Year | 69.0% |
| Venue | 64.2% |
| Citations | 32.6% |
| Abstract | 74.0% |

**按源分布**：
- arxiv: 169篇（元数据较好）
- core: 158篇（**citation/year/venue 大量为空**）
- crossref: 91篇
- openalex: 70篇
- semantic_scholar: 仅30篇（限流导致）

### 环节2：评分（Scoring）— 权重设计有问题

#### 问题2.1：评分区分度不足
**实测数据**（高优先级15篇）：
- 最高分：0.802
- 最低分：0.755
- **分差仅 0.047**，区分度极低

15篇高优先级论文中，真正直接相关 "GNN + test oracle" 的仅约 5 篇，其余是 GNN 用于电路检测、bug 预测等间接相关论文。但评分系统给了它们几乎相同的高分。

#### 问题2.2：authority 权重仍不足以区分
当前权重：`relevance=0.25, authority=0.30, recency=0.15, novelty=0.15, idea_potential=0.15`

**问题**：
- 高优先级论文中 11/15 篇 citations=0，但 authority 分数没有被显著压低
- 代码中 `if (paper.citation_count or 0) == 0 and paper.year is None: authority_adj = score.authority * 0.7`，但只惩罚 year 完全缺失的，citation=0 但 year 有值的论文不受惩罚
- **TOGA**（Test Oracle Generation的经典论文，citations=10）分数 0.755，与 citations=0 的论文几乎无差异

#### 问题2.3：LLM评分缺乏跨论文校准
每篇论文独立调用 LLM 评分，LLM 倾向于给"看起来相关"的论文都打高分（0.7-0.8），没有横向比较机制。

### 环节3：报告生成（Report）— 质量尚可但有隐患

#### 优点
- STORM 两步式生成（大纲→逐节填充），7个章节
- 引用覆盖完整：50篇论文全部被引用 [P1]~[P50]
- 无 [unsupported] 标记（说明引用都是有效的）
- 长度 22,481 字符，内容充实

#### 问题3.1：RAG 在 Windows 上禁用，报告仅基于摘要
```python
# runner.py line 275
logger.info("Task %s: skipping RAG indexing (disabled on Windows, using abstract fallback)", task_id)
```
报告只能基于论文摘要（≤600字符/篇），无法获取方法细节、实验数据等深度信息。

#### 问题3.2：中文乱码问题
数据库中报告内容存储为 UTF-8，但在 Windows GBK 环境下读取显示为乱码。这是显示层问题，不影响内容质量，但影响调试。

#### 问题3.3：Wiki 知识库可能引入二次幻觉
Wiki 由 LLM 从论文摘要编译，如果 LLM 在编译时产生幻觉，这些幻觉会被带入报告和 Idea 生成阶段。

---

### 环节4：Idea 生成 — 幻觉严重，5个Idea全部被拒

#### 问题4.1（核心问题）：related_paper_ids 大量幻觉

**实测数据**（5个Idea的引用追溯）：

| Idea | Decision | Score | 引用论文 | 有效引用 | 幻觉引用 |
|------|----------|-------|----------|----------|----------|
| 1 | reject | 0.112 | 2篇 | 0 | **2篇全部幻觉** |
| 2 | reject | 0.107 | 2篇 | 1 | 1篇幻觉 |
| 3 | reject | 0.062 | 2篇 | 1 | 1篇幻觉 |
| 4 | reject | 0.0 | 4篇 | 3 | 1篇幻觉 |
| 5 | reject | 0.0 | 2篇 | 0 | **2篇全部幻觉** |

**关键发现**：`2cc30b49-a0b0-468d-85d8-2d7f8008e53e` 这个 paper ID 在 **5个Idea中被引用了5次**，但它根本不在论文库中！

**根因**：
- `IDEAS_SYSTEM` prompt 要求 LLM 填写 `related_paper_ids`，但 LLM 会编造看起来合理的 UUID
- 代码中有验证逻辑 `valid_ids = [pid for pid in item.related_paper_ids if pid in valid_paper_ids]`，但过滤后 valid_ids 可能为空，Idea 仍然被保存
- **没有对 valid_ids 为空的 Idea 做拒绝处理**

#### 问题4.2：基线（baseline）幻觉严重

**实测数据**（trace 记录）：
```json
{
  "verified": 4,
  "fabricated": 7,
  "fabricated_names": ["TOGA框架", "TOGLL框架", "TOGA框架", "TOGA框架", "TOGA框架", "TOGA框架", "TOGLL框架"]
}
```

5个Idea中检测到 7 个虚构基线名称。`TOGA` 虽然是真实的测试oracle方法，但 LLM 在 method_sketch 中将其用作框架名时语境不正确。`TOGLL` 则是完全虚构的。

**验证逻辑问题**：
- `KNOWN_REAL_BASELINES` 白名单包含 "memgpt", "rag" 等，但不包含 "TOGA"
- 搜索验证逻辑 `if name_lower in title_lower` 使用子串匹配，"TOGA" 可能匹配到不相关的论文标题
- 虚构基线惩罚 0.15/个，最多 0.3，但最终分数已经被其他问题压到极低

#### 问题4.3：数据集幻觉

**实测数据**：
```json
{
  "suspicious_datasets": [
    "Defects4j数据集", "SF110数据集", "BLEU-4", "APFD", 
    "Oracle生成的准确率", "基线：TOGA框架", "TOGLL框架", "MemGPT",
    "Defects4j数据集", "自定义的代码数据集", "故障覆盖率", "准确率"
  ]
}
```

**根因**：正则提取 `数据集[：:]\s*(.+?)(?:\n|$)` 会贪婪匹配整行，把"基线"、"评估指标"等内容也当作数据集名。

#### 问题4.4：5层验证形同虚设

5层验证设计：
1. LLM 去重 + metric 检查 → 检测到 4 个 metric 问题
2. 基线搜索验证 → 检测到 7 个虚构基线
3. 数据集验证 → 检测到 12 个可疑数据集
4. Novelty check → 搜索失败时仅扣 0.05
5. 评分 → 最终全部 reject

**问题**：验证机制能检测到问题并扣分，但 **没有阻止低质量 Idea 进入数据库**。5个 Idea 全部 reject 后触发 retry，retry 又触发了新一轮搜索，最终 30 分钟超时崩溃。

#### 问题4.5：method_sketch 格式不规范导致解析失败

LLM 生成的 method_sketch 没有严格遵循 `基线：` `数据集：` `评估指标：` 的格式，导致正则提取失败或提取到错误内容。

实测 Idea 4 的 method_sketch 片段：
```
...基线：TOGA框架、TOGLL框架、MemGPT
```
这里 `TOGLL框架` 和 `MemGPT`（MemGPT是记忆系统，与测试oracle无关）被列为基线，明显是幻觉。

### 环节5：流程编排（Runner）— 超时与资源问题

#### 问题5.1：30分钟超时导致流程未完成
```
2026-07-20 18:21:25 任务启动
2026-07-20 18:44:49 RAG索引开始（idea retry阶段）
→ 30分钟超时，任务中断
```

**根因**：
- 5轮搜索 + 评分每轮约3-4分钟
- Wiki ingest 6个batch约2分钟
- 报告生成约2分钟
- Idea第一轮 reject → 触发 retry → 额外搜索一轮 + RAG + Wiki + Idea再生成
- 总耗时轻易超过30分钟

#### 问题5.2：Idea retry 循环效率低
当 Idea 全部 reject 时：
1. 触发新一轮搜索（Round 6）
2. 对新论文做 RAG 索引（下载 PDF + embedding）
3. Wiki 重新 ingest
4. 重新生成 Idea

这个循环最多 3 次，每次都要重复完整的搜索→评分→RAG→Wiki→Idea流程，代价极高。

## 三、链路问题因果关系图

```
检索源限流(S2 429)
    ├──→ 经典论文缺失（TOGA等高引用论文未被检索到）
    │       └──→ 报告和Idea缺乏对核心工作的引用
    ├──→ 元数据不完整（citation/venue缺失）
    │       └──→ 评分authority维度失准
    └──→ 检索精度低（不相关论文混入）
            └──→ 评分区分度不足（噪声论文也被打高分）

评分权重设计缺陷
    ├──→ citation=0的论文未被有效惩罚
    └──→ 高优先级论文分差仅0.047

Idea生成幻觉根源
    ├──→ LLM编造paper IDs（UUID格式，不在库中）
    ├──→ LLM编造baseline名称（TOGLL、LangGSL等）
    ├──→ LLM编造dataset名称（或正则提取错误）
    └──→ RAG禁用 → Idea无法获取论文全文细节 → 只能靠LLM想象

5层验证的局限
    ├──→ 能检测问题但无法阻止低质量Idea入库
    ├──→ 正则解析依赖格式，格式不规范时失效
    └──→ retry循环代价过高 → 超时崩溃
```

## 四、优化建议（按优先级排序）

### P0：立即修复（影响Idea可用性）

#### P0-1：修复 related_paper_ids 幻觉
**方案**：在 `generate_ideas.py` 中，Idea 生成后立即验证 `related_paper_ids`：
```python
# 如果 valid_ids 为空，直接拒绝该 Idea，不保存
if not valid_ids:
    logger.warning("Idea '%s' has NO valid paper IDs — rejecting", item.title[:40])
    continue  # skip saving this idea
```

**更优方案**：在 prompt 中只提供 paper ID 列表，不给 LLM 生成 UUID 的机会：
```
可用论文ID列表（只能从此列表中选择）：
- 1ca049de: SCALE-GNN: Advanced Graph Reduction...
- 8f41c849: GUARD: A GNN-Based Tool...
...
```

#### P0-2：修复 baseline 验证逻辑
- 将 `TOGA` 加入 `KNOWN_REAL_BASELINES`
- 正则提取改为结构化 JSON 输出（让 LLM 返回 `{"baselines": ["TOGA", "RAG"], "datasets": ["Defects4j"], "metrics": ["accuracy"]}`）
- 搜索验证使用精确匹配而非子串匹配

#### P0-3：降低 Idea retry 代价
- 不再触发完整搜索轮，只对已有论文重新生成 Idea
- retry 时调整 prompt（更强约束、更少数量）
- 将 max_idea_rounds 从 3 降为 2

### P1：检索质量提升

#### P1-1：配置 Semantic Scholar API Key
```env
SEMANTIC_SCHOLAR_API_KEY=<申请key>
```
免费申请：https://www.semanticscholar.org/product/api#api-key-form

#### P1-2：添加检索结果预过滤
在 `search_and_save_papers` 中，对检索结果做相关性预过滤：
```python
# 使用 embedding 相似度预过滤，只保留与 topic 相关度 > 0.5 的论文
from sentence_transformers import SentenceTransformer
model = SentenceTransformer('BAAI/bge-base-en-v1.5')
topic_emb = model.encode(state.normalized_topic)
for paper in raw_papers:
    paper_emb = model.encode(paper.title)
    sim = cosine_similarity(topic_emb, paper_emb)
    if sim < 0.5:
        continue  # skip irrelevant
```

#### P1-3：修复 metadata_enrichment 限流问题
- 对 S2 元数据补充也使用 rate_limiter
- 补充失败时不影响主流程（已是 fire-and-forget，但并发太高）

### P2：评分优化

#### P2-1：增加 citation 惩罚
```python
# 当前：只惩罚 citation=0 AND year=None
# 改为：citation=0 时单独惩罚
if (paper.citation_count or 0) == 0:
    authority_adj = score.authority * 0.85  # 轻度惩罚
if (paper.citation_count or 0) == 0 and paper.year is None:
    authority_adj = score.authority * 0.6   # 重度惩罚
```

#### P2-2：引入跨论文校准
评分时提供同批次其他论文的标题列表，让 LLM 做相对比较：
```
本批次其他论文（用于横向比较）：
- Paper A: title...
- Paper B: title...
请相对其他论文评分。
```

### P3：Idea 生成深度优化

#### P3-1：启用 RAG（解决 Windows PyTorch 问题）
- 使用 Docker 或 WSL 运行 RAG 索引
- 或使用 API-based embedding（OpenAI embedding API）替代本地模型

#### P3-2：结构化 Idea 输出
将 method_sketch 从自由文本改为结构化 JSON：
```json
{
  "model_architecture": "基于GraphSAGE，在AST节点上做消息传递",
  "algorithm": "top-k pooling + contrastive loss",
  "datasets": ["Defects4j", "SF110"],
  "metrics": ["accuracy", "F1"],
  "baselines": ["TOGA", "standard LLM"]
}
```

#### P3-3：Idea 生成前注入已验证的 baseline/dataset 白名单
```
可用基线（只能从此列表选择）：TOGA, MemGPT, RAG, GPT-4, BERT, T5, CodeT5, GraphSAGE, GCN, GAT
可用数据集：Defects4j, SF110, HumanEval, MBPP, CodeContests
```

### P4：流程编排优化

#### P4-1：增加超时时间或分阶段执行
```python
AGENT_TIMEOUT = 3600  # 60 minutes
# 或将 Idea 生成拆为独立阶段，用户可手动触发
```

#### P4-2：搜索轮次自适应
当 dup_rate > 0.6 时提前终止，不需要等到 0.75。

## 六、总结

### 核心问题链
```
检索源限流 → 论文覆盖不全 + 噪声多
    → 评分区分度不足 → 高优先级论文质量参差
        → 报告基于有限摘要 → Idea缺乏grounding
            → LLM编造引用/基线/数据集 → 5层验证全部拦截
                → retry循环 → 超时崩溃
```

### 修复优先级
1. **P0**（1-2天）：修复 Idea 引用幻觉 + baseline 验证 + 降低 retry 代价
2. **P1**（2-3天）：配置 S2 API key + 检索预过滤
3. **P2**（1-2天）：评分权重调整 + 跨论文校准
4. **P3**（3-5天）：启用 RAG + 结构化 Idea 输出
5. **P4**（1天）：超时调整 + 搜索自适应终止

### 预期效果
- P0 修复后：Idea 引用幻觉从 100% 降至 < 10%
- P1 修复后：检索精度提升，经典论文覆盖率达 90%+
- P3 修复后：Idea method_sketch 有全文支撑，技术细节可信
- 整体：Idea 可用率从 0% 提升至 60%+
